情報を書く前に、置き場所、形式、量を決めます。リポジトリにファイルやディレクトリの責務の定義があれば、それに従います。

## 性質で置き場所を決める

| 情報の性質 | 置き場所 |
|:--|:--|
| 実行される正解（コマンド、値、構成） | コード、スクリプト、設定ファイル |
| 同じ形のレコードや、機械が読み書きする情報 | データファイル（JSON、YAML、CSV、JSONL） |
| なぜそう決めたか、どの案を退けたか | ADR |
| 人向けの目的、使い方、背景、設計 | `README.md`、`docs/` |
| エージェントに常に守らせる短いルールと責務の対応 | `AGENTS.md`、インストラクション |
| 特定の作業でだけ必要な手順や知識 | スキル |
| 複数プロジェクトで再利用するエージェント設定 | プラグインマーケットプレイス |
| 一時的な作業メモや計画 | コミットしない場所（セッションフォルダーなど） |
| 秘密情報 | リポジトリに置かない（環境変数、シークレットストア） |

迷ったときは「誰が、いつ読むか」で決めます。常に読み込まれる場所は最小限にし、必要なときだけ読む場所へ寄せます。

## 正本を 1 つにする

- 同じ内容を複数のファイルに書きません。正本を 1 つ決め、ほかからはリンクします。要約の再掲もしません。
- 実装を文章で言い換えません。コマンドや値はスクリプトや設定を参照させます。
- リンクは、読み手が次に必要とする情報へ張ります。リンク先の内容を繰り返しません。

## Markdown とデータを分ける

次のいずれかに当てはまる情報は、Markdown ではなくデータファイルにします。

- 同じ形のレコードが増え続ける（一覧、カタログ、対応表、ログ、メモの蓄積）
- スクリプトやエージェントが読み書き、検索、検証する
- 件数や値の整合性をテストで確かめたい

データファイルには、可能ならスキーマを添えます。人が読む表が必要なら、データから生成するか、データファイルへリンクします。

## 肥大化させない

- 追記の前に既存の記述を探し、修正や置き換えで済ませます。
- 古くなった記述は削除します。変更の経緯は Git の履歴と ADR に任せ、本文に履歴を残しません。
- 新しいファイルは、既存のどのファイルの責務にも当てはまらないときだけ作ります。その責務を 1 文で言えることを確かめます。
- 一度きりの出来事、自明なこと、一般知識は書きません。公式ドキュメントで分かることはリンクで済ませます。
- 常に読み込まれるファイル（`AGENTS.md`、インストラクション、`SKILL.md` 本体）は短く保ちます。詳細は必要なときだけ読む参照ファイルへ分けます。
- 大きくなり続けるファイルは、責務ごとに分割するか、データファイルへ移します。

## 責務を明文化する

ファイルやディレクトリの責務が曖昧なまま情報を増やしません。責務の定義がなければ、`AGENTS.md` などエージェントが常に読む 1 か所に、ファイルやディレクトリと責務の対応を短く書くよう提案します。新しい置き場所を作ったら、その対応も更新します。
