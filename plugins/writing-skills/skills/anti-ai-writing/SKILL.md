# Anti-AI Writing

AI にありがちな表現や構成の偏りを減らすために、静的な検出を行うスクリプトと、セマンティックなレビュー観点を提供するスキルです。

## 対応言語

- 日本語: [references/japanese.md](./references/japanese.md)
- 英語: [references/english.md](./references/english.md)

> [!TIP]
> 言語が混在している場合は、それぞれの言語のリファレンスを参照する。

> [!NOTE]
> 技術文書の構成、手順の書き方、誤読の余地の排除、用語の統一は `technical-writing` が担当する。このスキルは、AI にありがちな表現と構成の検出だけを扱う。

## 共通原則

- 抽象的な評価より、具体的な行動・対象・条件を書く。強い評価には根拠を添える。
- 立場と判断理由を示す。留保だけで結論を避けない一方、不確実なことまで断定しない。
- 実例・数字・専門用語は、確かめられるものを使う。人間らしさのために体験や感情、出典を捏造しない。
- 見出しの再宣言や儀礼的な前置きを削り、本題から始める。
- 同じ構文や段落構成を反復しない。重要な箇所と補足で分量やリズムに差をつける。
- 強調や括弧は必要な分だけ使う。em dash (`—`) は使わず、文を分けるか通常の句読点に置き換える。
- 読者と用途に合った文体を保つ。余談・会話調・感情表現は必要なときだけ使い、無理に構成を崩さない。
- 引用・固有名詞・技術用語の正確さを、表現上の好みより優先する。
- 現在の状態を書く。過去の経緯や旧版の説明を網羅しない。変更履歴の管理は Git などのツールに任せ、履歴がないと誤読される場合（移行手順、互換性、判断の理由）だけ書く。
- 読み手が必要とする抽象度で書く。1 回限りの出来事（日付、人名、案件名）を、抽象化しないまま一般論に混ぜない。反対に、抽象化しすぎて何の話か分からなくなる場合は、具体例を 1 つ添える。

## 作業手順

1. 読者・目的・伝える結論を確認し、共通原則と言語別リファレンスを制約として執筆・推敲する。
2. **短文でも省略せず**、対象の全文に [scripts/lint.py](./scripts/lint.py) を実行する。チャット内の文章は標準入力で渡すか、一時ファイルに保存する。
3. 各指摘を「直す」「文脈上残す」に仕分ける。検出語を一括置換したり、指摘を消すために事実や意味を変えたりしない。
4. 修正後は全文を再検査する。未確認の指摘がなくなり、残した表現の理由を説明できれば完了。指摘ゼロを目的に無限に書き直さない。
5. 最後に、論旨・根拠・読みやすさを通読で確認する。静的チェックでは判断できない部分も言語別リファレンスに沿ってレビューする。

診断だけを求められた場合は、指摘と修正案を返し、対象を書き換えない。スクリプトを実行できない場合はその理由を伝え、静的チェック済みとは報告しない。

## 静的チェックの実行

Python 3.10 以降の標準ライブラリだけで動く。パッケージのインストール、通信、モデルや辞書のダウンロードは不要。入力は UTF-8 のテキストまたは Markdown。スクリプトは入力を書き換えない。

自動検知する語句と正規表現は [scripts/rules.json](./scripts/rules.json) で管理する。単純な注意語は `terms`、構文パターンは `pattern` に追加する。各ルールの `severity` は `info`（参考情報）、`warning`（要確認）、`error`（使用禁止）のいずれかを指定する。用途と修正方針が異なる語は、同じ配列へ混ぜず別のルール ID とメッセージに分ける。

`<skill-directory>` を、このスキルを読み込んだ場所の絶対パスに置き換える。作業ディレクトリやリポジトリ内の配置を仮定しない。

```bash
uv run --no-project "<skill-directory>/scripts/lint.py" --language ja draft.md
uv run --no-project "<skill-directory>/scripts/lint.py" --language en draft.md --json
uv run --no-project "<skill-directory>/scripts/lint.py" --language both draft.md
```

`draft.md` の代わりに `-` を指定すると標準入力を読む。言語は `ja` / `en` / `both` を明示する。JSON は `file`、`language`、`findings` を持ち、各指摘に `rule`、`severity`、1 始まりの `line` / `column`、`message`、`excerpt` を含む。

終了コードは `0` = 指摘なし、または `info` のみ、`1` = `warning` / `error` あり、`2` = 引数・入力・ルールデータのエラー。`1` は実行失敗ではなく、レビューすべき指摘があることを示す。

コードフェンス・インラインコード・インデントされたコード行・先頭の YAML front matter・HTML コメント・URL・Markdown のリンク先は検査から除外する。見出し・箇条書き・引用の本文やリンクの表示文は検査する。Markdown 処理と文境界の判定は簡易的なもので、完全な構文解析ではない。

検出は語句・記号・反復のヒューリスティックに限る。形態素解析、意味解析、事実確認、AI 生成確率の採点は行わない。指摘がなくても、文章の品質や人間による執筆を保証しない。
