# 日本語の表現チェック

共通原則と作業手順は [SKILL.md](../SKILL.md) を参照。以下は日本語の文章を推敲する際のチェックポイントであり、該当したからといって機械的に書き換えるのではなく、文脈に照らして判断する。

## 記号・書式

- 行末をコロン（`：` / `:`）で終えて次の行や箇条書きへつなぐ書き方は避け、「ポイントは以下の通りです。」のように文として閉じる（「項目：説明」のように同じ行の中で使うコロンは構わない）。
- 「」の中に『』を重ねるのは、引用文の中のさらなる引用や書名・作品名を表す場合に限る。言葉を目立たせるためだけに鉤括弧を重ねない。
- 補足や留保を括弧（）に詰め込みすぎない。文脈上必要な条件なら本文に組み込み、不要な注釈なら削る。
- 見出し、スライドのタイトル、表の見出しセルに句点（。）を付けない。読点（、）も基本は使わない。語句は中黒（・）や「と」「や」で並べる。読点で句を区切りたくなるほど長いなら、タイトルに書く内容が多すぎるので、要点だけに絞る。
- 箇条書きの項目は、完結した文なら句点で閉じ、語句や体言止めなら付けない。1 つのリストの中で揃える。
- 読点は、読み誤りを防ぐ位置に打つ。主題の後、長い修飾が続く境目、接続の前後、並列の区切りが主な位置になる。息継ぎやリズムで打たない。1 文に読点が 4 つ以上並ぶのは、語句の並べ立てでなければ、文が長すぎる合図である。2 文に分ける。
- 読点がない文も避ける。漢字やひらがなが続いて読み誤る箇所には、読点を入れる。

## 語尾・リズム

- 「〜です。〜です。」のように同じ語尾を3文以上続けない。ただし、重複を避けるために「です・ます調」のなかに「だ・である調」を混ぜるのではなく、文をつなぐか述語の形（「〜ます」「〜でしょう」など）を変えて調整する。
- 文頭の「さらに」「また」「したがって」「そのため」の多用を控える。削っても文のつながりが分かるなら省き、残す場合も1段落に1回程度を目安にする。
- 「以上がポイントです」「次に進みましょう」「最後にまとめます」といった定型の案内文で段落を閉じない。

## 語彙・構文

- 「サポートする」「提供する」のような抽象的な動詞は、具体的に何をするのか（「毎週レポートを送る」など）まで踏み込んで書く。
- 「非常に有効」「大きなメリット」「革新的」「包括的」といった強い評価語は、裏付けや比較対象が伴わないなら削る。
- 「本質的」「最適化」「多角的」「不可欠」などの硬い抽象語が続く箇所は、具体的な説明に噛み砕く（専門用語として必要な場合はそのまま残す）。
- 羅針盤、設計図、エンジン、土台、車の両輪、架け橋、スパイス、レシピ、筋トレ、DNA、潤滑油といった紋切り型の比喩に頼らない（技術用語や文字通りの意味で使う場合を除く）。
- 「正本」「照合」のような硬い管理用語や、「静かに壊れる」「黙って失敗する」「ここが境界になる」「別物になる」といった AI 特有の大げさな言い回しは、文脈に合った平易な表現にできないか見直す。
- 「フリーランサー」ではなく「フリーランス」、「デーティングアプリ」ではなく「マッチングアプリ」のように、日本語として定着している語を選ぶ。
- 「〜することができる」は「〜できる」や直接的な動詞に詰める。
- 「〜に他ならない」のような大げさな強調は、本当に必要な箇所にだけ絞る。
- 「検証を行う」「調査を実施する」は「検証する」「調べる」のように、具体的な動詞にできないか確認する。
- 「利用者」「ユーザー」「エンドユーザー」のように、同じ対象を段落内で言い換え続けない。1 つに決めて繰り返す。用語の定義と表記の一貫性は `technical-writing` が扱う。
- 感覚を述べる文は、仕組みか数値に置き換える。「データベースが身近になる」は「`.toSQL()` が送信する SQL をそのまま返す」のように、読者が知ること、することを書く。他のプロジェクトの文書にそのまま載る文は、何も伝えていないので削る。
- 述語を落として圧縮しない。体言止めの連続、助詞の抜けた箇条書き、「→」でつないだ文は、述語のある文にする。「入力不正 → 終了コード2、書き込みなし」は「入力が不正なら、終了コード 2 で終了し、何も書き込まない」と書く。
- 「単なる〜ではなく」「〜にとどまらず」で対比を作らない。主張を直接書く。
- 「〜と言われています」「専門家によると」「一般的に」は、誰が言っているのかを示す。示せなければ削る。
- 「今後の発展が期待されます」のような、どの文書にも置ける締めは、具体的な予定や次の行動に置き換えるか削る。
- 太字のラベルとコロンで始まる箇条書きは、ラベルが本文を繰り返しているなら散文にする。ラベルが新しい情報を足すなら残してよい。
- 「ステップ1：〇〇」のような見出しパターンを乱用しない。後から手順番号で参照する必要がある場合のみ番号を振る。
- 「以下の3つの観点から説明します」のように、直後の見出しを見れば分かる内容を本文で繰り返さない。

## スタンス・導入

- 「一概には言えませんが」「〜と言えるでしょう」で結論をぼかさない。まず結論や判断を示したうえで、前提条件や例外を補足する。
- 「結論から言うと」と切り出すなら、前置きを挟まず直後に結論を書く。
- 「メリットもあればデメリットもあります」という両論併記で終わらせず、どんな条件ならどちらを選ぶべきかまで書く。
- 「あまり推奨されません」のような遠回しな否定は避け、なぜ避けるべきか理由を添えてはっきり書く。表現の強さは読者との関係性に合わせる。
- 「ご質問ありがとうございます」のような儀礼的な挨拶や、「いかがでしたか」といった定型の締めくくりは、チャットや記事の用途上必要な場合を除いて省く。
- 「ぶっちゃけ」「正直なところ」などの砕けた前置きや読者への問いかけは、書き手自身の普段の文体に合う場合だけ使う。

## 内容と抽象度

- 過去の経緯を全部書こうとしない。「当初は A だったが、その後 B に変わり、さらに C が加わった」と時系列を並べず、現在の状態だけを書く。変更の履歴は Git や変更履歴のファイルに任せる。
- 経緯を残すのは、読み手が履歴を知らないと誤る場合に限る。旧版からの移行手順、互換性が切れる条件、「なぜ今の形なのか」の理由が該当する。残すときも、現在の状態を先に書き、経緯は 1 文に絞る。
- 1 回限りの出来事を、そのまま一般的な説明に混ぜない。「10 月 21 日の障害で」「田中さんが指摘した」は、日付や人名を外し、そこから言える性質や条件に直す。出来事そのものが目的の文書（障害報告、議事録）では、そのまま書く。
- 抽象化しすぎない。「適切に設定する」「問題が起きたら対処する」のように、何を指すか分からない文は、対象と値、条件を書く。抽象的な説明だけでは伝わらない場合は、具体例を 1 つ添える。例には、確かめられる事実を使う。
- 抽象度に迷ったら、この文章を誰が、どんな場面で読む可能性があるかを想像する。読み手と場面の候補を挙げていくと、抽象度をどのあたりに置くかの見当がつく。決め打ちの規則ではなく、迷ったときに使う観点である。

## 修正例

| 型 | 直す前 | 直した後 |
| --- | --- | --- |
| 経緯の羅列 | 「当初は CSV で保存していたが、v1.2 で JSON に変更し、その後 JSONL も追加した。」 | 「結果は JSONL で保存する。」 |
| 必要な経緯 | 「保存形式が JSON から JSONL に変わった。」 | 「結果は JSONL で保存する。v1.1 以前の JSON ファイルは、`convert` コマンドで変換できる。」 |
| 出来事の混入 | 「10 月 21 日の障害で、接続数が上限に達した。」 | 「接続数が上限の 100 に達すると、新しい接続は失敗する。」 |
| 抽象化しすぎ | 「エラーは適切に処理する。」 | 「入力が不正なら、終了コード 2 で終了する。たとえば、日付が `2024-13-01` のときは、月が範囲外だと表示して止まる。」 |
| 軽い動詞 | 「パフォーマンスの検証を実施しました。」 | 「検索 API の応答時間を 100 回測りました。」 |
| 感覚の描写 | 「データベースが身近に感じられます。」 | 「`.toSQL()` は、データベースに送る SQL 文字列をそのまま返します。」 |
| 過度な圧縮 | 「入力不正 → 終了コード2、書き込みなし」 | 「入力が不正なら、終了コード 2 で終了し、何も書き込みません。」 |
| 対比の型 | 「単なるツールではなく、チームの文化を変える存在です。」 | 「レビュー待ちの時間が平均 2 日から 4 時間に減りました。」 |
| 曖昧な出典 | 「一般的に、早めの共有が有効と言われています。」 | 「リリースの 3 日前までに共有すると、手戻りが減りました。」 |
| 汎用的な締め | 「今後の発展が期待されます。」 | 「次は、負荷試験の結果を 11 月に追記します。」 |

直した後の例は書き換えの方向を示すものであり、事実ではない。実際の文章では、確かめた事実と数値だけを使う。

## 通読で判断する項目

語尾や文の区切りの判定は文字列表現に基づく簡易的なものであり、品詞や構文までは解析しない。略語・引用・箇条書きなどでは文の区切りがずれる場合があるため、指摘箇所は必ず原文の文脈で確認する。また、上記のチェックポイントのうち、根拠の有無・比喩の妥当性・文体の統一・訳語の自然さなどはスクリプトでは検出できないため、通読して判断する。
