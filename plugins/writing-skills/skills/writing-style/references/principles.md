# 原則

文章の役割は、人間の読み手が、必要なときに、必要な情報を、読みやすい形で受け取れるようにすることです。書くときも直すときも、最初に読んでください。言語別のリファレンスや technical.md の規則は、この原則の下にあります。

## 読む場面と結論を先に決める

書き始める前に、誰が、いつ、どこで、何のために読むのかを決めます。通勤中にスマホで流し読みするのか、作業の合間に手順書を見返すのか、会議で投影されたスライドを見るのかで、必要な情報も並べる順序も変わるからです。場面が決まったら、読み手にしてほしいことと結論を決め、結論と理由を先に置きます。前置きは省いて、本題から入ります。

## 媒体の形に合わせる

同じ内容でも、媒体の形によって書き方は変わります。縦にスクロールする画面（記事、README、チャット）では、読み手は上から下へ流し読みします。Nielsen Norman Group の視線計測では、文字の多いページで、冒頭の行と各行の左端に視線が集まっていました（[F 型](https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/)）。要点を段落や行の頭に置き、見出しだけ拾っても流れが分かるようにすれば、この読まれ方に合います。

文字の少ない横長のレイアウト（スライドなど）では、デザインの経験則として、視線が左上から右下へ Z 型に動くものとして配置を考えます。1 枚に 1 つの主張を置き、先に読ませたいものを左上に寄せます。細かい決め方は媒体ごとに違うので、迷ったら、読み手が実際に読む画面を思い浮かべてください。

## つながりは文で書く

理由、条件、対比のように、内容どうしにつながりがあるときは、箇条書きに分けず、文でつなぎます。箇条書きにすると「だから」や「しかし」が消えて、読み手がつながりを補うはめになるからです。リストが向くのは、手順のように順序がある内容や、並べて見比べる独立した項目です。項目を一文でつなげられるか試し、つながるなら散文にします。

## 確かめられることで書く

「劇的に」のような強い評価語を足したくなったら、数値や具体的な動作で言い切れないかを考えます。言い切れないなら、その語は削ります。体験談や出典は、よく見せるために作りません。確かめていないことは、確かめていないと書きます。

## 根拠は主張の近くに置く

読み手は、意外な事実や初めて知る数値に出会うと、本当だろうかと立ち止まります。確かめる手段が近くにないと、読み手は疑ったまま読み進めるしかありません。数値、事例、出典の URL で補強できるなら、基本的には補強します。ただし、読み手がすでに知っている前提まで補強する必要はなく、どこまで示すかは場面で決めます。

補強するときは、置き場所も読み方に合わせます。視線が止まった場所の近くに置き、本文の流れを切らない形にします。脚注に対応した Markdown や静的サイトジェネレーターなら、脚注が自然です。ふつうの Markdown なら、文の直後に `（出典: [名称](URL)）` のように括弧で添えます。スライドなら、主張や数値の右肩に、小さな文字で出典を添えます。どの形でも、URL を裸で貼らず、何の出典かが分かる名前を付けてください。

## 既存の文章を直すとき

文体と想定読者は、原文に合わせます。原文の確信度も変えません。推測を言い切りにしたり、条件付きの判断を事実のように書いたりすると、書き手の主張そのものが変わってしまうからです。引用、固有名詞、技術用語は、言い換えの好みより正確さを優先します。

## 規則より読み手

働いていない語は削り、平易な語を選びます。「ということになります」は「です」に、「当該ファイル」は実際のファイル名にします。ただし、規則に従うと文がかえって不自然になるなら、別の形に直すか、そのまま残して構いません。規則は、読み手が必要な情報を受け取れる文章にするための手段であって、守ること自体が目的ではありません。
